已思考（用时 4 秒）# 本轮对话总结

按时间线拆成五件事，每件点出**为什么这么改**，以及**卡在哪里**。

---

## 一、Windows 操作中心上/下一曲按钮是灰的

**现象**：操作中心里能播放/暂停，但上一曲/下一曲按钮灰色不可点。

**根因**：浏览器默认只自动接管 `play` / `pause` 两个动作，`previoustrack` / `nexttrack` 必须由开发者**显式**通过 `setActionHandler` 声明，否则系统认为应用不支持这两个操作，按钮保持禁用。

**改法**：在 `_Layout.cshtml` 播放器脚本的 IIFE 末尾追加 5 个 handler：

```text
previoustrack / nexttrack / play / pause / seekto
```

**为什么放在 IIFE 末尾**：

- 那里能直接访问闭包里的 `queue` / `index` / `load` / `audio`，逻辑和 `btnPrev` / `btnNext` 的监听器完全一致，不会行为分叉。
- 只在脚本初始化时跑一次，`setActionHandler` 重复注册会让 SMTC 重新握手，也会造成抖动。

**配套改动**：闭包状态区加 `_lastMetaHash`，并把 `MediaMetadata` 的写入从 `updateUI()` 里抽成独立的 `updateMediaSession(it)`，按 `hash` 去重。

---

## 二、第一次改法直接把播放搞炸了

**当时做法**：把 `new MediaMetadata(...)` 直接写在 `updateUI()` 里，`setActionHandler` 追加在末尾。

**结果**：播放直接炸。

**收敛过程**：具体炸点未定位，但把 metadata 写入收进独立函数、并给 `setActionHandler` 加 `try/catch` 之后，播放恢复正常。

**留下的经验**：`MediaMetadata` / `setActionHandler` 的调用对**位置和异常**比较敏感——包在独立函数里、加容错，比散在 `updateUI()` 中更稳。这一版完整 `_Layout.cshtml` 已经贴给你，播放确认正常。

## 三、切歌时操作中心闪烁

**症状演变**：

| 阶段 | 现象 |
| --- | --- |
| 加 _lastMetaHash 前 | 任何操作都闪（每次 updateUI() 都写 metadata） |
| 加 _lastMetaHash 后 | 暂停不闪，切歌才闪 |

**"暂停不闪"这一条本身就是关键证据**：说明去重生效了，`_lastMetaHash` 挡住了所有不改歌的路径（暂停、拖进度、音量、静音）。

**剩下的闪来自哪里**：切歌时 `hash` 真的变了 → 写新 `MediaMetadata` → Windows 把整张媒体卡片**拆掉重建**（重新解析封面、重排布局）→ 视觉上闪一下。这不是 Web 层的 bug，而是 SMTC 收到元数据变更后的固有反应。

**试过的两条缓解**：

1. 加 hash 去重 → 挡掉非切歌路径 ✅，挡不住真正换歌 ⚠️
2. 去掉 `artwork`（只写 title / artist）→ 减小重建开销，但**闪烁仍在** ⚠️

**未试的两条**：

- 把 metadata 写入时机挪到 `audio` 的 `playing` 事件（新歌真正出声那一刻才写），避免"旧卡 → 空卡 → 新卡"的中间态
- 如果部署在 WebView2 / Blazor Hybrid 里，由宿主 C# 侧 `SystemMediaTransportControls` 统一接管 SMTC，Web 层完全不碰

**当前决定**：先不解决，功能不受影响。

## 四、顺手排除了 Detail.cshtml

**排查动因**：怀疑是不是 Detail 页的渲染/事件逻辑在反复触发 metadata 写入。

**结论**：不会。`Detail.cshtml` 从头到尾**没有任何一行碰 `navigator.mediaSession`**，它和 SMTC 之间隔着一层 `MvPlayer` 公共 API 和一个 `player:change` 事件。

里面唯一两处值得注意的调用：

- `render()` 末尾调 `MvPlayer.refresh()` → `updateUI()` → `updateMediaSession()`，但 `_lastMetaHash` 已挡住重复写。
- `onPlayerChange` 里对**所有**曲目行按钮重写 `innerHTML`，只影响页面内 DOM，不碰操作系统。

**所以排查范围锁定在 `_Layout.cshtml` 的播放器脚本内。**

## 六、留给后续的线索

如果哪天要回头啃闪烁，按代价从低到高：

1. **加探针**：在 `updateMediaSession()` 里打 `console.log('[SMTC] write', hash)`，跑一次切歌，确认**到底写了几次**。若发现 >1，闪烁立刻有解。
2. **挪写入时机**：从 `load()` → `updateUI()` 挪到 `audio.addEventListener('playing', ...)`。
3. **宿主接管**：若部署在 WebView2，去掉 Web 层所有 `mediaSession` 调用，改由 C# 侧 `SystemMediaTransportControls` 统一维护。

功能层面这轮已经到达可用状态，闪烁属于观感优化，随时可以停在这里。
